# Replace Infinite Chunk Generation with a Finite Deterministic Dungeon Floor

## Objective

Inspect the existing repository and replace the current infinite, independently generated chunk-based world generation with a **finite, deterministic, server-generated dungeon floor**.

The entire floor must be generated as one coherent world at server startup or floor initialization. Runtime chunks should then be created as spatial slices of that completed floor solely for rendering, networking, streaming, collision loading, and performance.

The primary dungeon layout should be based on Bob Nystrom’s **“Rooms and Mazes”** procedural generation approach:

1. Place non-overlapping rooms.
2. Fill the unused solid space with maze passages.
3. Track each room and maze as a distinct connectivity region.
4. Find possible connectors between regions.
5. Open enough connectors to join the entire dungeon.
6. Add selected extra connectors to create loops.
7. Prune some—but not necessarily all—dead ends.
8. Apply biome-specific geometry, elevation, landmarks, hazards, and decoration.
9. Validate the completed floor.
10. Divide it into the project’s existing runtime chunk format.

The game uses both a **tile map and a height map**. The new generator must treat elevation as a first-class part of dungeon generation rather than adding random per-tile height noise afterward.

Do not stop after writing a proposal. Inspect the existing architecture, make reasonable architecture-compatible decisions, implement the system, test it, and document the important configuration values.

---

# Non-Negotiable Requirements

## Finite floor

The dungeon is no longer infinite.

A floor must have configurable finite dimensions, such as:

```text
floorWidth
floorHeight
```

Use the project’s existing coordinate units. Do not assume one generation cell must equal one rendered tile.

Tiles outside the finite floor should behave according to the existing engine’s conventions, such as:

* Solid wall
* Void
* Out of bounds
* No chunk available

Do not procedurally extend the floor when a player approaches its edge.

## Server authoritative

The server generates the canonical floor.

Clients should receive the same chunk data they receive now where practical, but those chunks must come from the completed server floor rather than being independently generated.

Do not require clients to reproduce generation unless the existing architecture already intentionally supports that.

## Deterministic

Given the same:

* World or run seed
* Floor number or floor ID
* Generator version
* Generation configuration

The generated floor must be identical.

Do not use unseeded random functions such as `Math.random()`.

Generation must not change based on:

* Chunk request order
* Entity update order
* Object iteration order
* Number of connected players
* Timing
* Thread scheduling

Use stable iteration order anywhere it could affect generation.

## Whole-floor generation before runtime chunking

Do not generate layout separately inside each runtime chunk.

Generate global arrays or equivalent structures for the entire floor:

```text
tileMap
heightMap
biomeMap
regionMap
featureMap or metadata
```

Only after generation and validation should these be divided into runtime chunks.

## Preserve existing architecture where reasonable

Before changing code, inspect:

* Existing world-generation entry points
* Server startup and floor initialization
* Current chunk interfaces
* Tile map representation
* Height map representation
* Collision and walkability rules
* Pathfinding
* Client/server chunk messages
* Save/load behavior
* Existing world seed handling
* Tile definitions
* Entity spawn systems
* Tests and debug utilities

Adapt the new system to the existing project instead of creating an unrelated parallel engine.

Preserve existing public interfaces when possible. It is acceptable to add an adapter that makes the completed floor appear through the current chunk provider interface.

# Suggested Architecture

Implement generation as a sequence of explicit deterministic passes rather than one large generator method.

A suitable conceptual structure is:

```text
FiniteFloorGenerator
    createGenerationContext()
    initializeSolidFloor()
    createBiomeRegions()
    reserveMandatoryFeatures()
    placeRooms()
    growMazes()
    connectRegions()
    addLoops()
    pruneDeadEnds()
    assignRoomAndCorridorRoles()
    generateElevation()
    placeElevationTransitions()
    applyBiomeGeometry()
    placeLandmarksAndFeatures()
    materializeTiles()
    validateFloor()
    partitionIntoRuntimeChunks()
```

Use the naming and patterns already established by the project.

Prefer small passes that receive:

```text
generation state
configuration
named deterministic random source
```

Avoid hidden mutable global state.

## Semantic generation versus visual tile selection

Where compatible with the current architecture, separate the semantic dungeon from its rendered tile IDs.

For example, generation may first produce cells such as:

```text
SOLID
FLOOR
ROOM_FLOOR
CORRIDOR
DOOR
ARCHWAY
STAIR_UP
STAIR_DOWN
RAMP
WATER
DEEP_WATER
PIT
BRIDGE
LEDGE
HAZARD
VOID
```

A later materialization pass can select the actual tile IDs using:

* Semantic cell type
* Biome
* Neighbor configuration
* Elevation
* Room or corridor role
* Existing autotiling rules

Do not discard the current tile-map implementation if it already provides a good equivalent abstraction.

# Logical Generation Grid

The Rooms and Mazes algorithm commonly works well on an odd-coordinate lattice where passages are carved in two-cell increments.

Do not blindly assume that one logical maze cell should equal one rendered tile.

Inspect:

* Player collision footprint
* Existing corridor width
* Character size
* Wall thickness
* Stair and ramp dimensions
* Current art scale

Support a configurable logical scale if necessary:

```text
generationCellScale = 1, 2, 3, etc.
```

For example, a one-cell logical maze corridor may materialize as a two- or three-tile-wide gameplay corridor.

The logical map may be generated first and expanded into the final tile and height maps, or the algorithm may operate directly on the tile map if that fits the current architecture.

The final dimensions do not necessarily need to be odd. Internally, the generator can pad or normalize its working dimensions and crop or wall off the unused border.

# Generation Pipeline

## 1. Initialize the finite floor

Start with every cell solid and non-walkable.

Create the required generation maps and initialize metadata to invalid or unassigned values.

Add a permanent solid boundary around the floor so rooms and maze passages cannot reach the external edge unless a specific boundary feature is intentionally placed.

## 2. Generate biome districts

Create a small number of large, contiguous biome districts before room and maze generation.

For a reasonably large first floor, target approximately three to five districts. Make this configurable based on floor area.

Possible techniques include:

* Seeded multi-source flood fill
* Weighted Voronoi regions on a coarse grid
* Coarse-grid noise followed by connected-component cleanup
* Graph-based district growth

Requirements:

* Each district should be contiguous or nearly contiguous.
* Avoid tiny biome islands.
* Merge regions smaller than a configurable minimum area into a neighboring biome.
* Smooth extremely jagged borders.
* Keep district shapes irregular rather than rectangular.
* Create explicit transition bands where two biomes meet.
* Do not produce a checkerboard of biome tiles.
* Each biome should occupy a meaningful part of the floor.

The biome map should influence geometry generation, not merely tile decoration.

## 3. Reserve mandatory structures and feature stamps

Before growing the maze, reserve space for major features that need predictable geometry.

Examples:

* Starting room
* Floor exit or stairwell
* Landmark rooms
* Large arena
* Shop or safe room
* Biome-specific centerpiece
* Bridge chamber
* Cistern
* Industrial processing hall
* Optional treasure branch
* Transition structure between biomes

Treat these as special room regions with one or more connection ports.

The maze and region-connector passes should connect these features naturally.

Create a reusable feature-stamp interface rather than hardcoding every landmark directly into the primary generator.

A feature stamp should be able to define:

```text
footprint
allowed biomes
minimum clearance
semantic tiles
elevation shape
required entrances
optional entrances
protected cells
spawn markers
tags
```

Initially, only a small number of stamps is required. The important part is creating an extensible system.

## 4. Place rooms

Attempt to place non-overlapping rooms throughout the floor.

Use biome-specific parameters for:

* Room count
* Minimum size
* Maximum size
* Aspect ratio
* Spacing
* Shape selection
* Probability of irregular rooms
* Density

For the baseline algorithm:

* Prefer odd room dimensions on the logical lattice.
* Prefer odd room positions where required by the maze lattice.
* Reject rooms that overlap existing rooms or reserved features.
* Include configurable padding between ordinary rooms.
* Assign each accepted room a unique connectivity-region ID.
* Mark the room floor as carved and walkable.
* Store room bounds, biome, center, entrances, area, and region ID.

Support rectangles first, but structure room placement so additional shapes can be added:

* L-shaped rooms
* Cross-shaped rooms
* Circular approximations
* Rooms made from overlapping rectangles
* Authored room stamps

Avoid adding complex shapes in a way that destabilizes the initial implementation.

Rooms should generally belong to one biome. Reject or adjust candidates that cross too much of a biome border unless they are explicit transition rooms.

## 5. Grow mazes through remaining space

For each uncarved logical cell that can begin a maze:

1. Assign a new region ID.
2. Grow a maze using randomized depth-first carving or a growing-tree equivalent.
3. Move in cardinal directions.
4. Carve the intermediate cell and destination cell.
5. Continue until that maze region cannot expand.
6. Repeat for every remaining valid solid area.

Use a directional persistence parameter rather than choosing every direction uniformly.

Conceptually:

```text
If continuing in the previous direction is possible,
usually continue straight.

Sometimes choose another valid direction,
based on the configured winding or turn probability.
```

This parameter should be biome-sensitive.

The result should contain:

* Rooms
* Maze corridors filling most unused space
* Multiple disconnected region IDs that will be connected afterward

Do not perform runtime chunk generation during this stage.

## 6. Find possible region connectors

Scan solid cells and identify cells that separate at least two distinct carved regions.

A valid connector candidate is generally a solid cell with carved neighbors belonging to different region IDs.

Store:

```text
position
adjacent region IDs
biome
possible connector type
```

Do not immediately open every candidate.

Avoid connector positions that would create invalid geometry, overlap reserved features, or conflict with height-transition footprints.

## 7. Connect all regions

Use a disjoint-set/union-find structure or an equivalent region-merging algorithm.

Shuffle connector candidates deterministically.

For each candidate:

* Determine which current region sets it touches.
* If it connects two or more disconnected sets, open it.
* Merge those sets.
* Record the opened connector.
* Remove or deprioritize nearby redundant candidates where necessary.

Continue until every required floor region belongs to one connected navigation component.

A connector can later materialize as:

* Open passage
* Door
* Archway
* Breached wall
* Gate
* Short bridge
* Stair or ramp landing

The exact visual form should depend on biome and context.

## 8. Add loops

A purely tree-shaped dungeon is undesirable.

After mandatory connectivity is complete, open some additional connector candidates according to configurable loop parameters.

Extra connectors should:

* Create meaningful alternate routes
* Avoid opening several adjacent wall cells that merely produce one large accidental breach
* Prefer routes that connect graph areas with meaningful path distance between them
* Be more common near hubs and major rooms
* Occasionally create biome-crossing shortcuts
* Remain deterministic

A simple probability is acceptable initially, but improve it by evaluating the graph distance that the new connector would bypass.

Prefer connectors that create a useful loop over connectors that only save two or three steps.

Expose configuration such as:

```text
extraConnectorChance
minimumLoopPathSaving
connectorSpacing
targetLoopCount
```

Exact names should follow project conventions.

## 9. Prune selected dead ends

Run iterative dead-end detection on maze corridor cells.

A dead end is generally a removable corridor cell with only one traversable neighbor.

Do not necessarily remove every dead end.

Protect:

* Rooms
* Opened connectors
* Spawn and exit areas
* Mandatory routes
* Landmark approaches
* Secret areas
* Treasure branches
* Elevation transitions
* Feature stamps
* Deliberately retained ambush or reward pockets

Use biome-specific pruning behavior.

Some biomes should retain more dead ends than others. This creates exploration space and prevents the dungeon from looking uniformly optimized.

Possible controls:

```text
deadEndRemovalFraction
deadEndRetentionChance
maximumPruneIterations
protectedBranchMinimumLength
```

# Biome Requirements

Implement the biome system as data-driven configuration where practical.

The initial floor should support at least the following conceptual biome profiles. Adapt their names to the project if equivalent biome definitions already exist.

## Maintenance Warrens

Geometry:

* Small rooms
* High corridor density
* Frequent turns
* Narrow passages
* More dead ends retained
* Small maintenance closets
* Occasional irregular junction chambers

Elevation:

* Mostly one primary level
* Small raised service platforms
* Short stairs
* Occasional shallow trenches or lowered pipe channels

Features:

* Pipes
* Utility alcoves
* Locked maintenance doors
* Vent-like shortcuts
* Storage rooms
* Dense local loops

The area should feel cramped and maze-like.

## Flooded Cistern

Geometry:

* Fewer rooms
* Larger open chambers
* Curved or irregular basin footprints
* Perimeter paths
* Bridges and causeways
* Fewer tiny corridor branches

Elevation:

* Lower basin floors
* Raised walkways
* Sunken water areas
* Ramps or stairs down into the district
* Bridges above non-walkable or hazardous low areas

Features:

* Shallow water
* Deep water or pits where supported
* Drain channels
* Islands
* Pump rooms
* Broken bridges
* Flood gates

Do not scatter water randomly. Water should occupy coherent basins based on elevation and room geometry.

## Collapsed Habitation

Geometry:

* Higher room density
* Rectangular and clustered rooms
* Apartment-like or office-like divisions
* Courtyard rooms
* Broken internal walls
* More grid-like corridors than the warrens

Elevation:

* Split-level rooms
* Short staircases
* Partially collapsed floors
* Raised interior platforms
* Sunken courtyards

Features:

* Barricades
* Rubble
* Breached walls
* Former living or commercial spaces
* Side rooms and searchable dead ends

The district should feel constructed and then damaged, not naturally cavernous.

## Industrial Processing

Geometry:

* Medium and large rooms
* Long straight corridors
* Wider passages
* Large machinery chambers
* Strong loops around central structures
* Fewer arbitrary twists

Elevation:

* Raised platforms
* Ramps
* Catwalk-like paths
* Trenches
* Pits
* Tiered processing rooms

Features:

* Machinery footprints
* Conveyors where supported
* Tanks
* Hazard lanes
* Control rooms
* Gated shortcuts

The biome should have a noticeably different room-size and corridor-turn distribution from the warrens.

## Biome transitions

Biome changes should not happen as a hard visual line across an ordinary room.

Create transition spaces such as:

* A maintenance tunnel opening into a cistern
* Flooded habitation rooms
* Pipes entering an industrial chamber
* Rubble becoming natural or eroded stone
* A checkpoint between constructed districts
* A stairwell connecting districts at different base elevations

Transition zones may blend the material sets of both neighboring biomes.

# Height-Map and Elevation Generation

## General rule

Do not generate independent random height values per tile.

Elevation should form coherent:

* Rooms
* Platforms
* Basins
* Terraces
* Corridors
* Trenches
* Ramps
* Staircases
* Ledges

The height map must agree with the tile map and the game’s actual movement rules.

Inspect the existing movement and pathfinding code before implementing this pass.

## Elevation representation

Use the existing height-map representation.

If heights are integer levels, define a configurable floor range such as:

```text
minimumElevation
maximumElevation
```

For Floor 1, a modest range such as three or four meaningful levels is probably sufficient unless the existing engine is designed for more.

Do not change the meaning or scale of existing heights without updating all consumers.

## Assign elevation by regions, not isolated cells

After base topology is connected, build an abstract navigation graph whose nodes may include:

* Rooms
* Major corridor sections
* Landmarks
* Biome districts
* Junctions
* Feature stamps

Assign coherent base elevations to these nodes.

Start the spawn area at a safe default elevation.

Traverse the graph deterministically and usually assign neighboring regions:

* The same elevation
* Occasionally one level higher
* Occasionally one level lower

Clamp elevation to the configured range.

Biome configuration should influence elevation:

* Cisterns trend downward.
* Industrial platforms may trend upward.
* Habitation may contain split levels.
* Warrens remain comparatively flat.

Do not require an elevation change on every graph edge.

## Legal height transitions

Every traversable height change must use geometry supported by the game.

Examples:

* Stair up
* Stair down
* Ramp
* Ladder, if supported
* One-way drop, if supported
* Small step, if the movement system allows it

Rules:

* Do not create an ordinary walkable edge across an illegal height delta.
* Do not create a stair or ramp without enough physical footprint.
* Stairs and ramps must align with their direction of travel.
* Their tile-map semantics and height-map values must agree.
* Ensure walls and collision prevent walking sideways through invalid height differences.
* Pathfinding must recognize the transition.

Reuse the game’s existing movement rules rather than implementing conflicting validation logic.

If the current pathfinder does not account for elevation, update or adapt it only as much as necessary so validation uses the same rules as player movement.

## Main-route elevation

The route from spawn to floor exit must always be traversable.

Avoid excessive elevation switching on the critical route.

The main route may include intentional elevation moments, but it should not become a staircase every few tiles.

## Height shaping inside rooms

Support coherent room-level features such as:

* Entire room at one elevation
* Raised perimeter
* Lower central basin
* Raised central platform
* Two terraces connected by stairs
* Trench through a room
* Bridge across a lower hazard
* Collapsed corner at a lower level

Use shape masks or feature stamps rather than random height noise.

## Corridors

Ordinary corridors should generally retain a stable height.

When a corridor connects regions with different heights:

* Reserve sufficient length for stairs or a ramp.
* Reshape the nearby corridor if required.
* Do not place an abrupt elevation change at a doorway unless the engine explicitly supports that appearance and movement.

## Single-surface limitation

If the existing height map only supports one traversable surface at each X/Y coordinate, do not generate true stacked walkable spaces or crossing tunnels at different elevations.

Bridges may still be represented as one walkable surface over a visual or hazardous lower tile if that matches the existing renderer and collision model.

Do not invent multi-layer traversal unless the engine already supports it.

## Height cleanup

Remove or repair:

* Isolated one-tile plateaus
* Single-tile pits
* Jagged stair-step noise
* Invalid diagonal cliff corners
* Unreachable elevated islands
* Stairs facing walls
* Ramps without a valid landing
* Doors opening into invalid height differences

# Landmarks, Progression, and Interesting Structure

After topology generation, create an abstract room-and-junction graph.

Use it to select:

* Spawn room
* Floor exit
* Main route
* Major landmarks
* Optional branches
* Hubs
* Secrets
* Shortcut candidates

## Spawn and exit

Place spawn and exit in suitable rooms, not arbitrary corridor cells.

Choose them using navigation-graph distance, not only Euclidean distance.

A good approach:

1. Select a valid spawn room.
2. Find distant reachable room candidates.
3. Select the exit from rooms near the far side of the navigation graph.
4. Require a configurable minimum route distance.
5. Reject placements with poor local space or invalid height access.

## Main route

Record at least one valid route between spawn and exit.

The generator does not need to force the player to follow it, but it is useful for:

* Protecting critical cells from pruning
* Encounter pacing
* Landmark placement
* Validation
* Avoiding accidental blockage
* Controlling elevation complexity

## Landmarks

Place memorable structures at useful graph locations:

* High-centrality hub
* Deep optional branch
* Biome center
* Major loop junction
* Location near a biome transition
* Area visible from another route but not immediately reachable

Aim for a recognizable landmark every several major rooms or runtime chunks, with density controlled by floor size.

## Optional routes

Include:

* Meaningful loops
* Long optional branches
* Secret-room clusters
* Shortcuts that reconnect distant graph areas
* Riskier direct routes
* Safer longer routes
* Locked or gated branches if the game supports them
* One-way drops only if gameplay supports reliable return routes

Do not make every optional area a single-cell closet.

# Biome-Specific Geometry Passes

After the core dungeon is connected, allow each biome to modify its area without breaking global connectivity.

Possible operations:

* Widen selected corridors
* Merge adjacent rooms
* Add partial walls
* Breach walls
* Carve small side chambers
* Add coherent water basins
* Insert platforms and trenches
* Add rubble
* Add columns or machinery footprints
* Convert junctions into chambers
* Add biome-specific loops

Every destructive or topology-changing operation must be followed by local or global validation.

Protect:

* Spawn
* Exit
* Main route where necessary
* Mandatory connectors
* Height transitions
* Reserved landmarks

Keep these transformations deterministic.

# Runtime Chunk Partitioning

After the completed floor passes validation, divide it into the project’s current runtime chunk dimensions.

For each runtime chunk, slice or reference:

```text
tile-map cells
height-map cells
biome metadata
static feature markers
collision data
static spawn markers
```

The chunk system should not rerun layout generation.

Prefer an adapter such as:

```text
getChunk(chunkX, chunkY)
```

that reads from the completed floor.

Requirements:

* Adjacent chunks must reconstruct the original global maps exactly.
* No seams may be introduced at chunk boundaries.
* Height transitions may cross runtime chunk boundaries.
* Rooms may cross runtime chunk boundaries.
* Biomes may cross runtime chunk boundaries.
* Runtime chunk boundaries must have no influence on dungeon geometry.
* Chunk-loading order must not influence content.
* Out-of-range chunk requests must be handled safely.

If neighbor halos are required for rendering, autotiling, lighting, or collision, provide those from the global floor without regenerating content.

Separate immutable base-floor data from mutable runtime state where appropriate:

```text
generated base tile
generated base height
destroyed or modified tile state
opened door state
looted container state
dynamic entities
```

Integrate with existing persistence rather than inventing a second save system.

# Random Number Streams

Derive named deterministic streams from the floor seed.

Conceptually:

```text
floorSeed = hash(runSeed, floorNumber, generatorVersion)

biomeSeed      = hash(floorSeed, "biomes")
featureSeed    = hash(floorSeed, "features")
roomSeed       = hash(floorSeed, "rooms")
mazeSeed       = hash(floorSeed, "mazes")
connectorSeed  = hash(floorSeed, "connectors")
loopSeed       = hash(floorSeed, "loops")
heightSeed     = hash(floorSeed, "heights")
materialSeed   = hash(floorSeed, "materials")
entitySeed     = hash(floorSeed, "entities")
```

Use the project’s existing seed and hashing utilities if available.

The purpose of named streams is to prevent a minor change in decoration from completely changing room placement.

Do not use language-default string hashing if it is unstable between processes or runtime versions.

# Validation and Deterministic Retries

Create a dedicated floor validator.

Validate using the same movement rules used by actual gameplay.

At minimum, verify:

## Bounds

* All generated coordinates are inside the floor.
* Boundary rules are respected.
* Runtime chunks do not expose uninitialized cells.

## Connectivity

* Spawn can reach exit.
* Every mandatory landmark is reachable.
* Every required biome is reachable.
* All ordinary rooms intended for gameplay are reachable.
* Doors and connectors connect valid spaces.

It is acceptable for deliberately inaccessible visual areas or pits to be excluded from this requirement.

## Height

* Every traversable height change is legal.
* Stairs and ramps have valid entrances and landings.
* No required area is isolated by elevation.
* No transition points into a wall or void.
* Pathfinding agrees with movement collision.

## Biomes

* No invalid biome IDs.
* No unintended tiny biome islands.
* Every generated biome meets configurable minimum area requirements.
* Biome transitions remain traversable.

## Gameplay spacing

* Spawn has sufficient open space.
* Exit has sufficient open space.
* Mandatory feature entrances are not blocked.
* Corridors meet minimum width requirements.
* Stairs and ramps meet footprint requirements.

## Runtime chunks

* Recombining all runtime chunks reproduces the global tile and height maps.
* Chunk-edge cells match neighboring chunks.
* No chunk performs random generation when requested.

## Retry behavior

If validation fails, retry deterministically using:

```text
attemptSeed = hash(originalFloorSeed, attemptIndex)
```

Cap retries at a configurable maximum.

The same original seed and configuration must select the same successful attempt.

Log validation failures with enough information to debug them.

Do not silently return a broken floor. After the retry limit, throw or return a structured generation failure according to existing server error-handling conventions.

# Automated Tests

Add tests consistent with the repository’s test framework.

## Determinism test

Generate the same floor multiple times and verify that all canonical generated data is identical.

Include at least:

```text
tile map
height map
biome map
spawn
exit
features
connectors
```

## Seed variation test

Verify that different seeds usually produce different layouts while still passing validation.

## Connectivity test

Generate multiple representative seeds and verify spawn-to-exit and mandatory-area reachability.

## Height-validity test

Verify that every movement edge obeys the project’s elevation rules.

## Biome test

Verify that biome regions:

* Exist in expected quantities for sufficiently large floors
* Meet minimum area constraints
* Do not contain unintended disconnected islands
* Have valid transitions

## Chunk reconstruction test

Partition a generated floor into runtime chunks, reconstruct the maps, and verify exact equality with the original floor.

## Boundary test

Verify that requests outside the finite floor are handled correctly.

## Property or seed-sweep test

Run validation across a useful set of seeds.

Keep the default test count fast enough for normal development. Allow a larger stress-test count for manual or CI execution.

## Generator version test

Ensure the generator version participates in seed derivation or persistence so future algorithm changes do not silently reinterpret old saved floors.

# Save and Compatibility Considerations

Inspect existing save behavior before choosing the persistence strategy.

At minimum, persist enough information to prevent saved games from unexpectedly changing when generator code changes.

Possible strategies:

1. Persist the complete generated floor.
2. Persist the seed, generator version, successful retry index, and all runtime modifications.
3. Use the project’s current world snapshot format.

Do not assume seed-only persistence is safe across generator-version changes.

Existing mutable world state must continue to work, including applicable systems such as:

* Opened doors
* Destroyed walls
* Collected loot
* Defeated static encounters
* Activated features
* Modified heights or terrain, if supported

# Initial Scope Control

Implement a strong extensible foundation without attempting to create every possible dungeon feature immediately.

The first working version should include:

* Finite whole-floor generation
* Rooms-and-mazes topology
* Complete region connection
* Meaningful loops
* Configurable dead-end pruning
* Large contiguous biome regions
* Four differentiated biome profiles
* Coherent elevation regions
* Legal stairs or ramps
* Spawn and exit selection
* At least a small reusable landmark or feature-stamp system
* Runtime chunk partitioning
* Validation
* Debug visualization
* Automated tests

Do not spend excessive time on final decorative asset selection if the repository does not yet contain the necessary assets. Use semantic placeholders and existing tiles while preserving the architecture needed for biome-specific art.

---

# Implementation Quality Requirements

* Follow existing project style and conventions.
* Do not introduce a new framework without a compelling reason.
* Do not duplicate tile, pathfinding, or collision concepts that already exist.
* Avoid one giant generator class.
* Make passes testable independently where practical.
* Comment algorithmic intent and invariants, not obvious syntax.
* Keep generation deterministic.
* Keep runtime chunk lookup fast.
* Avoid generating gameplay topology on the client.
* Avoid coupling geometry to runtime chunk boundaries.
* Do not leave the old infinite generator as the active default.
* Remove obsolete code when safe, or clearly isolate temporary legacy compatibility.
* Do not break unrelated gameplay systems.

Before finalizing, run the project’s normal:

```text
build
type checking
linting
tests
generation seed sweep
```

Fix failures caused by the change.

# Definition of Done

The work is complete when:

1. Starting a server generates one finite dungeon floor.
2. The same seed and generator version produce the same floor.
3. The floor contains rooms embedded in maze-like passages.
4. All required dungeon regions are connected.
5. Extra connections produce meaningful loops.
6. Dead ends are pruned selectively rather than uniformly.
7. Multiple large biome districts are visibly and geometrically distinct.
8. The height map contains coherent elevation features rather than tile noise.
9. Every required elevation change is traversable through legal stairs, ramps, or supported transitions.
10. Spawn and exit are reachable and sufficiently separated.
11. Runtime chunks are slices of the completed floor.
12. Runtime chunk boundaries do not affect generation.
13. Existing chunk-loading and networking behavior continues to work or is cleanly adapted.
14. Invalid floors are detected and deterministically retried.
15. Tests verify determinism, connectivity, height validity, biome validity, and chunk reconstruction.
16. Development tools make biome, region, height, route, and chunk boundaries inspectable.
17. The new finite generator replaces the current active infinite world generator.

At completion, provide a concise implementation summary containing:

* Files added
* Files changed
* Existing systems integrated with
* Generation pipeline
* Important configuration values
* Validation strategy
* Tests added
* Known limitations
* Recommended next procedural-generation improvements
