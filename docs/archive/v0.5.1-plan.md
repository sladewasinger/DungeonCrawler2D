# v0.5.1 -- Visual Fixes

Status: Released 2026-07-26

v0.5.1 is a visual-correction patch following the v0.5.0 renderer-memory work.
It must not change world generation, stair physics, networking, room access, or
the authoritative simulation. It fixes the presentation and interaction
defects documented below:

1. North-south stairs currently render as flat tiles with debug horizontal line
   art instead of readable stepped ramps.
2. The safe-room attendant's speech bubble can be hidden behind room void or
   terrain occluders, and the attendant is labeled `Nib, Food Attendant` even
   though the intended role is `Safe Room Attendant`.

## Issue 1 -- North-south stairs are not rendered as stairs

### Observed symptom

In the 2D renderer, screen-horizontal stairs look like a coherent ramp with
colored stepped bands. Screen-vertical stairs look like a dark rectangle or
floor tile with thin horizontal stripes. The stripes read like a barcode, not
like climbable steps.

### Root cause

The renderer intentionally takes two different paths in
`packages/client/src/render/terrain/drawStairSurface.ts`:

- When `screenDirection` is horizontal, `stairRenderState()` sets `sideStair`.
  `drawSideStair()` then fills five full-height bands using the sampled ground
  height and `heightTint()`. This is the readable ramp treatment.
- When `screenDirection` is vertical, `sideStair` is false. The renderer draws
  a flat floor, overlays `pickStairFrame(FRAME_STAIRS_NS)`, and adds thin
  horizontal riser rectangles through `drawStairTreads()`.

`FRAME_STAIRS_NS` is literal debug tileset line art. It is not a perspective
stair surface. The current visual asymmetry is therefore a rendering-branch
problem, not a generation or physics problem. `stairScreenDirection.ts` already
remaps world climb direction into screen direction; preserve that contract.

### Required implementation

Replace the direction-specific visual split with one stepped-surface renderer
that works for all four screen climb directions.

The renderer must:

- Draw five filled, elevation-tinted bands for both axes.
- Use vertical bands when the climb is screen-horizontal.
- Use horizontal bands when the climb is screen-vertical.
- Sample `world.groundAt()` along the correct local axis:
  `world.groundAt(wx + band.sample, wy + 0.5)` for vertical bands and
  `world.groundAt(wx + 0.5, wy + band.sample)` for horizontal bands.
- Add a clear high-facing edge highlight to each step, with north/south and
  east/west high-end orientation handled correctly. Do not always highlight
  the same physical side.
- Preserve the existing `liftPx`, light tint, height tint, camera orientation,
  and depth-container behavior.
- Never use `FRAME_STAIRS_NS` or `FRAME_STAIRS_EW` as the primary stair surface.
  Those debug frames may remain for debug/gallery assets, but production stair
  presentation must not depend on their line art.
- Remove the current flat-floor-plus-line-art treatment. `drawStairTreads()`
  may remain only as a subtle accent after filled steps exist; it must not be
  the only indication that a stair is present.
- Keep the output pixel-art sharp and compatible with the native-resolution
  terrain bake planned for v0.5.0.

### Suggested structure

Generalize `sideStair.ts` into an axis-aware helper rather than duplicating two
renderers. The existing `sideStairBands()` pure profile can remain the shared
five-band geometry. Add an explicit screen-axis/high-end input, for example:

```ts
type StairAxis = "x" | "y";

drawSteppedStairSurface({
  axis: stacksVertically(screenDirection) ? "y" : "x",
  highAtStart: screenDirection === 0 || screenDirection === 3,
  ...
});
```

The exact API is implementation-defined, but the axis and high-end direction
must be explicit. Do not infer them from whether the current tile happens to
be brighter or darker.

### Stair tests and evidence

Add or update focused tests for:

- Five contiguous bands covering the tile for both axes.
- Height samples using the correct x or y local coordinate.
- Mirrored high-end orientation for north versus south and east versus west.
- All four screen directions after `screenClimbDirIndex()` remapping.
- No production stair path selecting `FRAME_STAIRS_NS` or
  `FRAME_STAIRS_EW` as its base art.
- Preserved positive and negative elevation lifts.

Capture visual evidence for a one-tile and multi-tile stair in all four camera
orientations. A reviewer should immediately identify each stair as a ramp from
the screenshot without relying on the player standing on it.

## Issue 2 -- Safe-room attendant speech bubble is occluded

### Observed symptom

The safe-room NPC speech bubble is partially cut off by a dark void/terrain
region. The bubble currently sorts at the attendant's ordinary world depth, so
room terrain strips or void occluders can draw over it.

### Root cause

`packages/client/src/render/rooms/roomPresentation.ts` creates and updates the
bubble with `attendant.depth + 0.4`. That is only a small same-row entity bias;
it is not a presentation overlay. The terrain renderer is allowed to have a
larger depth for the void or occluder strip, so the bubble disappears behind
the room geometry.

### Required implementation

- Define a named safe-room presentation depth in `roomPresentation.ts` or the
  shared depth module. It must be above all terrain pages, void strips, normal
  entities, and entity labels, while remaining below the separate HUD scene if
  the scenes share a camera.
- Set the speech bubble to a dedicated bubble depth above the attendant and
  nameplate, for example `SAFE_ROOM_BUBBLE_DEPTH` and
  `SAFE_ROOM_BUBBLE_DEPTH + 1` for deterministic ordering.
- Reapply that fixed depth whenever the room objects are repositioned or the
  speech text is refreshed. Do not derive it from `attendant.depth`.
- Ensure the text background, stroke, and all wrapped lines use the same object
  and depth, so no portion of the bubble can be occluded independently.
- Keep the bubble centered over the attendant, within the camera viewport when
  practical, and preserve word wrapping. This patch is about depth and
  readability; do not silently remove or truncate speech text.
- Add a regression test around the room presentation depth contract. If Phaser
  object integration is difficult to unit-test, extract a pure depth resolver
  and test that it is greater than the terrain/entity depth range.

## Issue 5 -- Unlit floor is too bright and player light does not light the ground

### Observed symptom

Large areas outside torch halos remain much brighter than the intended dungeon
atmosphere. The player's personal light reads as a small glow around the player,
but it does not visibly brighten the floor tiles the way a torch does. The target
is stronger contrast: unlit floor should become substantially darker while the
brightness and color of already-lit torch areas remain unchanged.

### Current lighting architecture

The next agent must preserve the existing split between baked terrain lighting
and dynamic light halos:

- `packages/client/src/render/terrain/tileLight.ts` computes a wall-aware BFS
  light field (levels `0..14`) while each terrain chunk is baked. The shipped
  `DEFAULT_TILE_LIGHT_CONFIG` uses `ambient: 0.65`, `curveFullLevel: 4.5`, and
  `warmth: 0.75`.
- `levelCurve()` maps the ambient floor toward a full-brightness plateau. A
  source at or above `curveFullLevel` must continue to render at exactly the
  current full brightness after this issue is fixed.
- `packages/client/src/render/lighting/pool.ts` renders pooled additive
  `light_soft` sprites. The personal source currently has a small radius and a
  deliberately reduced alpha, so it is a halo cue rather than a tile-light
  source.
- `DynamicLightSeed` already supports transient tile seeds for thrown torches,
  but feeding a moving player seed into every terrain chunk every frame would
  trigger expensive dynamic texture rebakes and is not an acceptable default.

### Required implementation

#### Darken only the unlit ambient floor

- Lower the live gameplay ambient value (or the equivalent level-0 tint) enough
  that unlit rooms read as clearly dark. Use a named constant/configuration,
  not a scattered multiply in the terrain renderer.
- Keep the lit plateau and torch color behavior unchanged. A tile at the full
  light level must produce the same tint/brightness as before; do not compensate
  for darker ambient by increasing torch halo alpha.
- Preserve biome grade, floor-height shading, chasm/void treatment, and the
  editor lighting-preview override contract. The editor may continue to tune
  `TileLightConfig`; live gameplay must still use one deterministic shipped
  default.
- Calibrate against screenshots or pixel samples: unlit floor must be visibly
  darker, while an existing torch-lit floor must be visually indistinguishable
  from the pre-change reference.

#### Evaluate bounded player-to-ground lighting

The player light may illuminate nearby ground, but do not implement a full
per-frame world rebake. Prefer the least expensive approach that reads as tile
lighting:

- First evaluate a pooled, local ground-light overlay using the existing
  `light_soft` asset or an equivalent pixel-aligned light cookie. It must render
  below entities and terrain occluders, use the player's `groundAt()` height,
  and fall off over a small fixed radius.
- Reuse sprites/objects; do not allocate a texture or sprite per tile per frame.
  Update only when the player crosses a tile or on a bounded throttle (no more
  than 10 updates per second while stationary/moving within the same tile).
- Bound the work to the visible neighborhood (for example a fixed 3x3 or 5x5
  tile footprint), cap the number of overlay objects, and avoid lighting through
  solid walls. The light must not brighten void/chasm cells that are not valid
  ground.
- If the existing BFS path is selected instead, seed only the nearby affected
  chunk(s) and rebake only on tile changes. Never rebuild all streamed chunks or
  run a full BFS on every render frame.
- Keep torch lights and their current brightness/coverage as the reference
  behavior. The personal light may add a neutral/warm floor contribution, but it
  must not wash out the existing torch palette or entity silhouettes.
- Include a cheap fallback: if the bounded ground-light pass is disabled by a
  performance guard, the personal halo remains functional and the ambient
  darkness change still applies.

### Performance gates and evidence

Measure before and after on a desktop browser and a representative low-end
mobile device. Record frame time, lighting/terrain update time, draw-call count,
overlay object count, and terrain rebake count while walking and standing still.
The player-ground-light pass is acceptable only if it adds no sustained
per-frame allocations, keeps the game within the existing 60 FPS budget on
desktop, and does not cause visible hitching or browser memory growth on mobile.
Capture reference screenshots of an unlit room, a torch-lit room, and the player
standing in darkness with the ground-light pass enabled. Include a screenshot
with a wall between the player and a floor patch to prove the light does not
leak through walls.

### Tests

Add focused tests for:

- The level-0/ambient tint becoming darker while a full-level tint remains equal
  to the previous shipped value.
- Player ground-light radius/falloff and wall blocking, using a pure helper if
  the Phaser overlay is difficult to test directly.
- Update throttling/tile-crossing behavior and the hard cap on pooled overlay
  objects.
- Preservation of torch light levels, floor-height offsets, biome grades, and
  void/chasm exclusion.

## Non-goals

## Issue 4 -- Exit-hall side walls are visual-only or missing collision

### Observed symptom

In the lower half of a personal room, the player can move under or beside the
dark void-wall shapes that flank the south exit hallway. Those shapes are meant
to seal the room and act as real walls, but the player can occupy the space
behind them. The same room template is used for party rooms and the shared safe
room, so all three room kinds must be audited and fixed together.

### Root cause to investigate

`packages/engine/src/world/features/rooms.ts` starts room chunks as a wall-filled
`64 Ã— 64` grid, carves the room interior, and then carves a two-tile south
alcove. The current tests verify only a small sample of the alcove shape. A
visual wall is not sufficient: the authoritative tile at every space beside
the exit hall must be `TILE.Wall`, whose collision is enforced by
`SOLID_TILES`/`World.isWalkable()`.

The next agent must inspect both sides of the contract:

- The generated server/client room chunk must contain solid wall tiles in every
  non-hall cell around the lower room edge.
- The client terrain view must render those exact wall tiles, not substitute a
  decorative void or a raised `TILE.Floor` that remains walkable.
- Server movement and client prediction must query the same room tile map. A
  client-only collision patch is not acceptable.

For every `personal`, `party`, and `safe` room template:

- The carved interior remains walkable floor only inside the declared room
  rectangle.
- The exit door remains at the center of the south wall.
- The designated two-tile south exit hallway remains walkable floor from the

- The cells immediately west and east of every hallway floor row are explicit
  `TILE.Wall` cells with the room wall height, not empty cells, decorative

- The wall height remains at least `ROOM_WALL_RISE`, and wall collision remains

- The hallway must not accidentally open into an adjacent chunk. If the final
  hallway depth or room placement changes, neighboring chunk cells must retain

Use explicit helper names such as `carveSouthExitHall()` and

### Collision and rendering requirements

- Verify `World.isWalkable()` returns false for both side walls at every hall

## Issue 7 -- Title description does not follow viewport resizing

### Observed symptom

On the title screen, changing the browser viewport after the page has loaded
leaves the tagline, premise, and controls description at their original
position. The form/door and other elements may respond to CSS or resize-driven
layout differently, so the description can overlap the door or drift away from
the title on a resized desktop window or a mobile landscape viewport.

### Current cause to verify

`packages/client/src/scenes/title/controlsHint.ts` creates a fixed-position
description section and calls `layout(window.innerWidth, window.innerHeight)`
only in its constructor. The method writes a pixel `top` value derived from
the initial height. There is no resize listener or shared responsive layout
owner that reapplies the position when the viewport changes. CSS `width` is
already relative, but the vertical anchor is not.

The next agent must also audit the neighboring title elements before choosing a
fix. `standaloneTitle.ts` owns the title and door, while `connectForm.ts` uses a
fixed bottom percentage. The final layout must establish intentional vertical
relationships between title, door, description, and character form rather than
making only the description follow the viewport.

### Required implementation

- Reapply title layout on `window.resize` and remove the listener in
  `TitleControlsHint.dispose()`.
- Use relative viewport units or a single responsive layout calculation for the
  description's vertical anchor (`%`, `vh`, or `clamp()` are acceptable). Do
  not preserve a stale initial pixel coordinate.
- Keep the description centered below the title/door composition, with enough
  separation that the premise and controls never sit on top of the door.
- Preserve the existing short-viewport behavior: hide the long premise and use
  compact controls when the height is below the defined threshold.
- Handle both width and height changes, including desktop window resizing,
  device rotation, mobile landscape, browser zoom/layout viewport changes, and
  the initial load path.
- Avoid a resize handler per title child when one shared layout owner can update
  the group. If multiple elements need updates, make their ordering and anchors
  explicit so later changes cannot reintroduce overlap.
- Keep text readable at narrow widths: allow wrapping, respect the viewport
  gutters, and do not introduce horizontal overflow.

### Tests and evidence

Add focused tests for:

- Recomputing the description position when height changes from a tall viewport

- Preserving the compact premise/controls selection at the short-height

- Keeping the description within viewport gutters at narrow widths and allowing

- Removing the resize listener on dispose so a destroyed title cannot mutate the

Capture before/after screenshots at minimum for:

## Issue 8 -- Touch controls remain visible after returning to desktop input

### Observed symptom

After using Chrome device emulation or otherwise switching between touch and
desktop input, the game can keep the virtual joystick, touch action buttons, and
touch-oriented HUD layout visible even after the user returns to a mouse and
keyboard viewport. This makes desktop play and planning difficult because the
mobile controls cover the dungeon and compete with keyboard/mouse affordances.

### Current cause

The current detector and lifecycle are capability-based and one-way:

- `packages/client/src/input/touchDetect.ts` returns true for `?touch=1`, the
  presence of `ontouchstart`, or `navigator.maxTouchPoints > 0`. Chrome's device
  emulation can leave those capabilities available even after the viewport is
  switched back to desktop mode, so they do not reliably describe the current
  input modality.
- `HudWidgets` and `InputController` snapshot `isTouchDevice()` at construction.
  Their late pointer handling can promote desktop to touch when a real touch
  arrives, but it never demotes touch back to desktop on keyboard or mouse
  activity. Once built, the touch widgets are not removed or hidden as a group.
- Other surfaces (`fakeData`, interaction prompts, Three HUD/input helpers)
  also consult the capability detector directly, so a local fix in one scene
  could leave inconsistent controls elsewhere.

### Required implementation

- Separate *input modality* from *touch capability*. Capability can inform the
  initial guess, but current `pointerType`, keyboard activity, mouse movement,
  and coarse/fine media-query changes must be allowed to update the active mode.
- Treat a trusted keyboard keydown or mouse move/button as desktop intent and a
  `pointerType === "touch"` interaction as touch intent. Do not switch on a
  synthetic mouse event generated immediately after a touch event.
- Use a small hysteresis/debounce window so a single stray event does not cause
  visible layout thrashing. A real keyboard/mouse interaction should still
  demote touch promptly enough that desktop users are not blocked by overlays.
- Make the mode transition shared and observable by both `HudWidgets` and
  `InputController` (and the Three route where applicable). Do not let each
  subsystem maintain an independent `touchActive` boolean.
- On a touch-to-desktop transition, hide or unmount the joystick, touch action
  buttons, touch-only bag affordance, and touch layout overrides; restore the
  desktop HUD positions and desktop interaction labels. On desktop-to-touch,
  mount/apply the touch layout exactly once and preserve existing touch state
  where safe.
- Keep explicit `?touch=1` behavior documented and deterministic for screenshots
  and testing. Decide and test whether explicit override locks touch mode or
  only supplies the initial mode; it must not become an unexplained permanent
  mobile overlay in ordinary desktop sessions.
- Reset active touch gestures and pointer capture safely during a mode change so
  a joystick drag, interact hold, or attack button cannot remain stuck.
- Re-evaluate mode on relevant viewport/orientation/media-query changes, but do
  not use viewport width alone as proof of a touch device. Desktop windows can be
  narrow and tablets can have keyboards/mice.

## Issue 9 -- Stale death-loot prompt appears without a nearby chest

### Observed symptom

The HUD can show a prompt such as `[E] open [DEAD] Austin's loot` while no loot

### Confirmed root cause

The prompt and action currently use different targeting contracts:

- `packages/client/src/scenes/dungeon/frameSync.ts` passes
  `buckets.lootChests[0]?.snap` directly into `resolveInteractionPrompt()`.
  That is the first loot chest in the current interpolated entity frame, not
  necessarily the nearest chest or one within `INTERACT_RANGE`.
- `packages/client/src/scenes/dungeon/interactionPrompt.ts` treats any supplied
  `lootChest` argument as nearby and creates the `[DEAD] ...'s loot` prompt
  without checking distance.
- `packages/client/src/net/lootChestQuery.ts` and
  `packages/client/src/input/gameplayActions.ts` do perform a distance check via
  `nearestLootChest()`. When the displayed chest is actually out of range,
  `useLootChest()` returns false, `[E]` falls through to ordinary interaction,
  and the server correctly has no nearby loot chest to open.

This is primarily a stale/false-positive prompt bug, not yet evidence that the
chest sprite failed to render. If a chest is truly within range after the prompt
fix, the next agent must separately audit the item entity's interpolation,
frame bucketing, `groundItemFrame("player-loot-chest")`, depth, and stale-entity
removal before calling it a renderer defect.

### Required implementation

- Make contextual loot prompts derive from the same nearest/in-range query as
  the `[E]` action. Do not pass an arbitrary first chest from a frame bucket.
- Set the authoritative death-loot chest lifetime to **5 minutes (300 seconds)**
  from creation. Keep the temporary killer/first-dibs lock as a separate rule;
  the lock must never extend the five-minute expiry.
- Preserve deterministic prompt priority: stairway, revive, nearby loot chest,
  world interaction, then ordinary pickup/selected-item help.
- Keep the server authoritative. The client may suppress a false prompt, but it
  must not infer that a chest can be opened when the server has not accepted the
  interaction.
- If multiple death chests are in the frame, select the nearest eligible target
  using the shared interaction range and stable tie behavior. The prompt's owner
  name and the chest id used by the action must refer to the same entity.
- When a valid nearby chest exists, verify that its rendered body/label uses the
  same entity id and position that the prompt/query selected. Do not fix the
  prompt by hiding a legitimately nearby chest or by widening the interaction
  range.
- Keep locked-chest behavior explicit: a nearby locked chest may show a clear
  lock/first-dibs state and `[E]` may send the intent, but a distant chest must
  never create a contextual prompt.

### Tests and evidence

Add focused tests for:

- A far loot chest producing no loot prompt and no loot interaction attempt.
- An in-range loot chest producing the named prompt and opening the matching
  stash when `[E]` is pressed.
- Multiple chests selecting the nearest one, with prompt owner/id matching the

## Issue 11 -- Unify death/revive presentation and revise revive rules

### Desired behavior

The downed state and ordinary death state should use one consistent death/revive
screen presentation, with state-specific copy and progress where needed. The
player should not encounter unrelated overlays or different interaction models
depending on whether a party member is present.
This issue supersedes the earlier 60-second, party-member-only revive behavior.

- **Ordinary death:** use a **15-second** respawn countdown.
- **Downed death while awaiting help:** use a **30-second** bleed-out window.
- **Revive eligibility:** any player may revive any other downed player;
  party membership is not required. The server must validate that the rescuer
  is eligible and close enough.
- **Revive duration:** completing a revive requires a continuous **4-second**
  interaction. Interruptions, range loss, incapacitation, or invalidation must
  cancel/reset the progress according to the interaction rules.
- Keep an intentional give-up/early-respawn path if retained, but make its
  timing and copy agree with the new 15-second/30-second model.

### Required implementation

Replace party-only revive gating and the existing death constants with named
state-specific configuration. Keep downed, bleeding-out, dead, and respawning
as explicit authoritative states rather than inferring them from HUD text.
The server owns countdowns, revive eligibility, progress, cancellation, and the
final state transition; the client renders the shared screen from snapshots and
may only predict visual progress.

The screen must clearly communicate the active state, remaining time, rescuer
identity when applicable, and the 4-second revive progress. It must remain
usable for solo players, party members, and unrelated nearby players without
exposing private state or allowing a client to force a revive.

### Tests and evidence

Add focused server/client integration tests for:

- Ordinary death using a 15-second respawn countdown.
- A downed player remaining revivable for 30 seconds before bleed-out.
- A non-party nearby player successfully reviving the downed player.
- Party and non-party revive attempts both using the same 4-second duration.
- Revive cancellation on movement/range loss, disconnect, rescuer incapacitation,
  duplicate revive, and bleed-out.
- Shared death-screen rendering for ordinary death and downed states, with
  correct state-specific text, timer, and progress.
- Server rejection of out-of-range, unauthorized, or stale revive requests.

Capture browser evidence with two unrelated players: one enters the downed
state, the other completes the visible 4-second revive, and the downed player
returns to play. Capture a second sequence showing ordinary death and the
15-second respawn countdown.

### Issue 11 definition of done

- Both death states use the shared death/revive screen presentation.
- Ordinary death is 15 seconds; party downed/bleed-out is 30 seconds.
- Any eligible nearby player can revive any downed player, regardless of party.
- Every revive takes four uninterrupted seconds and cannot be client-forced.
- Server, client HUD, input prompts, audio/animation cues, and documentation
  agree on the same state machine and timings.
