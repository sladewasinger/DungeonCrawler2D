# v0.5.0 — Performance Improvements

Status: Released 2026-07-26

v0.5.0 is a focused performance release. Its primary objective is to replace
the 2D terrain renderer's page-count-based resource strategy with a bounded,
device-aware memory strategy that is appropriate for pixel art and safe on
mobile hardware.

The release must preserve the current world scale, terrain appearance, camera
rotation, elevation, occlusion, and chunk-generation behavior. It changes how
terrain is rendered and retained, not how the dungeon is generated.

## Current diagnosis

Chrome's "Aw, Snap!" page means the browser renderer process was terminated or
crashed. Low frame rate would be the expected symptom of a CPU-limited phone;
the abrupt renderer failure after roughly thirty seconds is more consistent
with memory or GPU-resource pressure.

The current 2D terrain path has a specific memory hazard:

- A generated world chunk is `64 × 64` tiles.
- A displayed tile is `48 × 48` pixels because the 16-pixel source art is
  rendered at a world scale of three.
- A whole-chunk base terrain page is therefore `3072 × 3072` pixels.
- An uncompressed four-channel page has a minimum raw footprint of
  `3072 × 3072 × 4 = 37,748,736` bytes, or `36 MiB`.
- A strip page is `3072 × 512`, with a minimum raw footprint of `6 MiB`.
- A one-chunk streaming margin normally retains at least a `3 × 3` area around
  a mobile viewport. Nine base pages alone consume at least `324 MiB`; views
  crossing chunk boundaries can retain twelve to sixteen base pages, or
  `432–576 MiB`, before strip pages and every other game resource.
- The spare pools can retain 24 base pages and 96 strip pages. Their theoretical
  raw RGBA capacity is `24 × 36 MiB + 96 × 6 MiB = 1,440 MiB`.

These figures are minimum texture-storage estimates. Browser-side backing
stores, staging surfaces, framebuffer attachments, driver copies, atlases,
sprites, effects, JavaScript state, and Chrome's own process memory can make the
real footprint larger.

The spare limits are high-water capacities, not proof that every session
immediately allocates 1.44 GiB. However, movement, teleports, and camera
rotation can progressively allocate pages, and returning pages to a pool keeps
their GPU resources alive. That explains why a device may initially run the
game and then lose the renderer after continued play.

## Why pixel art uses so much texture memory today

The source artwork is small, but the baked terrain pages are not stored as
source sprites. Phaser composes terrain into full-resolution dynamic render
textures. Every pixel in the `3072 × 3072` destination consumes texture memory
even when it came from a 16-pixel tile, repeats another tile, or represents an
empty-looking region.

There is no requirement to store the three-times display scale in the texture.
The terrain can be baked at its native 16-pixel tile resolution and displayed
at three-times scale with nearest-neighbor filtering. Scaling an Image changes
the sampling transform; it does not allocate a second, enlarged copy of its
texture. A native-resolution whole-chunk page is `1024 × 1024`, or `4 MiB` raw
RGBA instead of `36 MiB`. This is a nine-times reduction before changing page
granularity.

Three design choices multiplied together:

1. Terrain is enlarged to display resolution before being baked, so the
   DynamicTexture caches all nine destination pixels for every source pixel.
2. Render-page dimensions are coupled directly to simulation chunk dimensions.
3. World geometry doubled generated chunks from 32 to 64 tiles per side while
   displayed tiles remained 48 pixels. Doubling both dimensions quadrupled the
   area and memory of each base page.
4. Streaming margins and spare pools are expressed in chunk/page counts rather
   than pixels or bytes. After the scale increase, one margin chunk means 3,072
   extra pixels in each direction, and every retained page is much more
   expensive than before.

The texture pool was introduced to avoid repeated framebuffer allocation
stalls. Reuse is still valuable, but the present pool trades those stalls for
an unacceptable memory high-water mark.

## Release scope

### 1. Bake terrain at native source resolution

This is the first implementation step and the largest immediate win. Keep the
world and camera at the existing 48-display-pixels-per-tile scale, but make the
terrain bake pipeline operate at 16 texture pixels per tile.

Introduce explicit renderer metrics instead of using `SCREEN_TILE_PX` for both
jobs:

```ts
export const TERRAIN_BAKE_TILE_PX = SOURCE_TILE_PX; // 16
export const TERRAIN_DISPLAY_SCALE =
  SCREEN_TILE_PX / TERRAIN_BAKE_TILE_PX; // 3
export const TERRAIN_BAKE_CHUNK_PX =
  CHUNK_SIZE * TERRAIN_BAKE_TILE_PX; // 1024
```

`SCREEN_TILE_PX` remains the correct unit for cameras, entity placement,
lighting placement, input projection, and the final world position of terrain
Images. `TERRAIN_BAKE_TILE_PX` is used only inside the terrain-rasterization
pipeline. Names and types should make it difficult to accidentally mix bake
pixels with display pixels.

Required changes:

- In `render/terrain/terrainPages.ts`, allocate base pages at
  `TERRAIN_BAKE_CHUNK_PX × TERRAIN_BAKE_CHUNK_PX`, making each base page
  `1024 × 1024` and approximately `4 MiB` raw RGBA.
- In terrain drawing helpers such as `placeSprite.ts`, `debugSprite.ts`, and
  `drawWallTile.ts`, position and size baked content with
  `TERRAIN_BAKE_TILE_PX`. Source atlas sprites should bake at scale one rather
  than `WORLD_PIXEL_SCALE`.
- Rename or separate `surfaceLiftPx` so its unit is unambiguous. Terrain-bake
  lift is `height × TERRAIN_BAKE_TILE_PX`; entity and final display lift remains
  `height × SCREEN_TILE_PX`.
- Convert door and structure drawing in `structures.ts` to bake-pixel
  coordinates. Replace display-pixel magic offsets with named bake-pixel
  constants.
- In `stripRows.ts`, express strip top, height, overhang, and padding in bake
  pixels. Prefer names such as `stripTopBakePx` and `stripHeightBakePx`.
- In `stripAtlas.ts`, make page heights and frame rectangles bake-pixel values.
  Re-select the strip page-height cap in source pixels instead of retaining a
  display-resolution constant by accident. A cap around 256–288 bake pixels is
  a starting point; the selected value must fit the tallest normal strip or
  deliberately use the existing dedicated oversized-page path.
- In `chunkVisualBuilder.ts`, maintain two distinct origins:
  `originBakeX/Y = baseV × TERRAIN_BAKE_TILE_PX` for drawing into pages, and
  `originScreenX/Y = baseV × SCREEN_TILE_PX` for positioning finished Images.
- Bake base and strip containers using the bake origin. Frame widths and heights
  passed to `DynamicTexture.add` must use bake dimensions.
- Place finished base and strip Images at their display/world positions and set
  their scale to `TERRAIN_DISPLAY_SCALE`. For a strip, convert its bake-pixel
  top back to display space exactly once.
- Force nearest-neighbor texture filtering for every finished terrain page.
  Keep Phaser's pixel-art configuration, but do not rely on an implicit default
  when a DynamicTexture can be marked explicitly.
- Keep page positions and camera projection integer-aligned so scaling one
  source texel produces an exact `3 × 3` block without seams or blur.

Do not implement this by merely adding `.setScale(3)` to the current finished
Images. The existing bake already contains three-times-scaled sprites and
48-pixel geometry; doing only that would scale terrain twice. The bake
coordinate system, sprite scale, strip frames, and output Image scale must
change together.

An optional low-risk migration technique is to apply a one-third transform to a
dedicated bake-root container while drawing into a 1024-pixel page. That
approach is acceptable only if focused tests prove Phaser applies the nested
container translation and scale exactly and screenshot comparisons show
pixel-identical output. Explicit bake-coordinate helpers are preferred because
their units are inspectable and testable.

Expected native-resolution memory:

| Residency | Current base pages | Native-resolution base pages |
| --- | ---: | ---: |
| One page | `36 MiB` | `4 MiB` |
| Nine pages | `324 MiB` | `36 MiB` |
| Twelve pages | `432 MiB` | `48 MiB` |
| Sixteen pages | `576 MiB` | `64 MiB` |
| 24-page spare capacity | `864 MiB` | `96 MiB` |

Strip texture content should receive the same nine-times area reduction when
both dimensions are converted to bake pixels. Pool caps must still be lowered;
native-resolution baking makes each mistake cheaper but does not justify
retaining unused resources indefinitely.

### 2. Replace page-count caps with byte budgets

- Track the estimated raw byte cost of every active and spare terrain page.
- Enforce separate active and spare budgets rather than assuming every page has
  a harmless fixed cost.
- Destroy released pages that would exceed the spare-byte budget.
- Maintain device profiles with substantially tighter mobile budgets.
- Consider reported WebGL limits, viewport size, device pixel ratio, and
  available device-memory hints when selecting a profile.
- Keep the budget conservative because raw texture dimensions do not include
  browser and driver duplication.

Initial targets to validate through profiling:

| Profile | Terrain active + spare raw target | Maximum preferred page |
| --- | ---: | ---: |
| Mobile / constrained | `≤ 96 MiB` | `1024 × 1024` |
| Desktop default | `≤ 192 MiB` | `1024 × 1024` |

These are starting ceilings, not permission to consume the entire budget.
Measurements on representative devices may justify lowering them.

### 3. Apply immediate containment

- Use no whole-chunk preload margin on constrained mobile devices.
- Reduce the mobile base-page spare count to approximately two to four.
- Reduce the mobile strip-page spare count to approximately eight to sixteen.
- Remove surplus dynamic textures from Phaser's texture manager instead of
  indefinitely parking them.
- Avoid releasing every resident page and reacquiring an equally large set in
  one camera-rotation frame.
- Place a hard guard on terrain texture dimensions so future world-scale changes
  cannot silently recreate this problem.

These changes should land with native-resolution baking. At native resolution,
four base pages cost approximately `16 MiB` instead of the current `144 MiB`.

### 4. Subdivide render pages only if measured residency still requires it

Native-resolution baking is simpler and should be measured before introducing
a second page grid. If whole `1024 × 1024` base pages still retain too much
offscreen terrain or cause allocation stalls, keep `64 × 64` simulation chunks
but subdivide their presentation into smaller independently baked render pages.

- A native-resolution `32 × 32` tile page is `512 × 512`, or `1 MiB` raw RGBA.
- A native-resolution `16 × 16` tile page is `256 × 256`, or `0.25 MiB` raw
  RGBA.
- Preserve deterministic page keys, terrain seams, elevation, occlusion bands,
  and all four camera rotations.
- Make page building cancellable when a page leaves the desired viewport before
  its bake completes.
- Determine desired render pages from the camera viewport plus a small,
  explicitly measured pixel or tile margin.
- Keep simulation chunk streaming independent from render-page residency.
- Prioritize pages intersecting the strict viewport and build margin-only pages
  incrementally within the frame budget.

Subdivision is not a substitute for native-resolution baking. If adopted, both
optimizations must be used together.

### 5. Preserve pixel-art quality

Optimization must not make the game blurry or reduce the intended three-times
pixel-art presentation.

- Keep nearest-neighbor sampling and integer-aligned placement.
- Verify that a source texel becomes one uniform `3 × 3` display block.
- Preserve exact terrain composition and depth ordering.
- Prevent seams, missing rows, stale page content, and rotation artifacts.
- Compare representative screenshots before and after the renderer change.
- Inspect procedural gradients, translucent contact shading, wall borders,
  stair bands, and fractional geometry. They will have one sample per source
  pixel rather than three; this is appropriate for pixel art, but must remain
  readable.
- Do not solve the problem by lowering source-art quality or indiscriminately
  shrinking the visible game canvas.

### 6. Implementation order

Implement and verify the work in this order so regressions have a narrow cause:

1. Add the bake/display metrics and unit tests for their exact values.
2. Convert terrain placement, lift, rectangles, gradients, debug edges, doors,
   and structure helpers to bake pixels.
3. Convert base and strip page allocation, packing, padding, and frame
   coordinates to bake pixels.
4. Update `chunkVisualBuilder.ts` to separate bake origins from display origins
   and scale completed Images exactly once.
5. Add focused tests for page dimensions, strip frame bounds, display placement,
   nearest filtering, camera rotations, and positive/negative elevation.
6. Capture pixel-comparison images for ordinary rooms, walls, deep faces,
   chasms, stairs, landmarks, doors, and every camera rotation.
7. Replace count-only spare caps with byte budgets and constrained-device
   profiles.
8. Measure steady-state walking, boundary crossing, repeated rotation, and
   teleport behavior on desktop and Android.
9. Introduce render-page subdivision only if those measurements show that
   native-resolution whole-chunk pages still miss the memory or frame targets.

## Acceptance criteria

v0.5.0 is not complete until all of the following are true:

- The 2D dungeon path never allocates a `3072 × 3072` terrain texture.
- Whole-chunk base pages, if retained, are exactly `1024 × 1024`, approximately
  `4 MiB` raw RGBA, and displayed at scale three with nearest filtering.
- Terrain is rasterized at 16 bake pixels per tile while cameras, entities, and
  final page placement remain at 48 display pixels per tile.
- No terrain object is scaled three-times both before and after baking.
- Terrain active and spare memory stays within the selected device profile's
  explicit byte budget.
- Walking, repeated camera rotation, chunk-boundary crossing, and teleports
  reach a stable memory plateau instead of continually increasing the terrain
  high-water mark.
- A constrained Android device can play continuously for at least fifteen
  minutes without an "Aw, Snap!" renderer failure.
- The renderer remains responsive while visible pages are baked and does not
  replace memory crashes with severe recurring allocation stalls.
- Existing terrain, elevation, occlusion, camera-rotation, and streaming tests
  pass.
- Pixel comparison captures show no unintended visual regression at page seams,
  walls, chasms, stairs, landmarks, or rotated views.
- Desktop behavior also uses bounded memory; mobile safety must not be achieved
  by leaving the 1.44 GiB theoretical pool intact for desktop.

## Expected player-facing release notes

### Added

- Added device-aware graphics resource limits for smoother play across phones,
  tablets, and desktop computers.

### Changed

- Changed dungeon terrain to bake at its native pixel-art resolution and scale
  sharply at display time instead of storing nine enlarged pixels for every
  source pixel.
- Changed terrain texture reuse to obey a strict memory budget.

### Removed

- Removed oversized display-resolution terrain textures and excessive spare
  texture retention.

### Fixed

- Fixed escalating terrain memory use that could cause Chrome to display an
  "Aw, Snap!" crash page during mobile play.
- Fixed world-scale changes multiplying renderer memory far beyond the visible
  pixel-art workload.
